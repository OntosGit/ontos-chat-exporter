# ONTOS · Исполнительский протокол археолога для существующего Codex

## Исходная цель
Находить в приватной истории ChatGPT замыслы, исследования, решения и архитектуры, которые не получили адресуемого продолжения. Не превращать каждую мысль в задачу. Наращивать общую способность ONTOS помнить, различать и продолжать работу.

## Фактические средства

- `tools/ontos_memory.py`: локальный SQLite, импорт, FTS5, `discover`, история источников, локальный реестр архитектур.
- Каноническая память `OntosGit/ONTOS.NODE` и checkpoint CPT-001.
- GitHub, Drive и Todoist через уже подключённые средства и текущие полномочия.
- Рабочая база данных и архивы ChatGPT хранятся только на личной машине. В открытый репозиторий их не передавать.

## Первый запуск (пилот)

1. Проверь, что владелец предоставляет локальный официальный ZIP-экспорт или JSON из существующего ONTOS Chat Exporter. Не притворяйся, что все чаты уже доступны; при отсутствии архива работай с синтетическим образцом и укажи точный входной материал, которого не хватает для реального пилота.
2. Выполни `import`, `stats`, `discover` и адресные `search` из `docs/ARCHITECTURE-MEMORY.md`. Не публикуй в облачные журналы текст приватных бесед.
3. Извлеки 10–20 кандидатных архитектур из **речи владельца**, восстанови по каждой самый ранний доступный первоисточник, развитие в последующих беседах, решения об изменении цели, отказы и потенциальные точки продолжения.
4. Для каждого кандидата проверь соответствие уже существующим архитектурам `ONTOS.NODE`, GitHub Issues/PR, Google Drive и Todoist. Различай: `already_realized`, `active_elsewhere`, `unstarted`, `research_open`, `superseded`, `requires_clarification`. Возвращай источники, а не догадку о состоянии.
5. Установи генеалогию для трёх контрольных случаев: реализованный замысел; действительно незавершённая архитектура; открытая концепция без необходимости хозяйственной задачи.
6. Через `record` и `attach` оформи три контрольные архитектуры в **локальной** базе с точными кандидатными ID. Через `link` свяжи только подтверждённые внешние объекты. Сверь `show` с первичной историей.
7. Запропонуй добавление в канонический граф только очищенной от приватного текста архитектурной записи с указанием происхождения. Todoist меняй только для доказанного открытого действия и после точной проверки отсутствия существующей карточки. Если фактов не хватает, оставь кандидата исследовательским.

## Что признаётся фактическим результатом

- Программа воспроизводимо импортировала и индексировала указанное число разговоров.
- Для каждого вывода существует идентификатор сообщения и проверяемая связь с контекстом, а не только фраза ассистента.
- Три архитектурных состояния отличаются без ложного дубля задач.
- Есть checkpoint, с которого другой исполнитель может продолжить без повторного чтения всей истории.
- Нет публикации личных чатов, новых внешних затрат, автоматического создания новых очередей и фальшивых утверждений об интеграции.

## Измерение

`candidate_count`, `confirmed_architecture_count`, `already_existing_count`, `new_valid_actions`, `duplicate_task_prevented`, `source_traceable_count`, `operator_interventions`. Число найденных фраз само по себе не качество.

**Ключевое правило:** сначала источник и история решения; только затем классификация; затем действительное продолжение. Если исследование обнаруживает три версии одной идеи, не создавать три новые задачи.
